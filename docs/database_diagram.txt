**Project:** Bibliotech

**Generated:** 2026-10-29  
**Database:** MariaDB / MySQL, InnoDB, `utf8mb4`  
**Schema sources of truth:** `bibliotech/backend/config/init.sql`, `bibliotech/backend/config/migrate_academic_groups.sql`, `bibliotech/backend/config/migrate_refinements.sql`, `bibliotech/backend/config/migrate_gamification.sql`, `bibliotech/backend/config/migrations/001_notifications.sql`

## 1. Overview

Bibliotech stores users, academic structure, learning materials, and the relationships that drive visibility, review, subscriptions, notifications and auditing.

- **20 tables**
- **30 foreign keys**
- **4 many-to-many tables** (`subject_professors`, `material_subjects`, `material_favorites`, `user_subscriptions`) plus unique-combination tables (`subscriptions`, `material_reads`, `reading_backlog`, `notifications`)
- Materials can belong to several subjects through `material_subjects`.
- Subjects can have several professors through `subject_professors`.
- Students subscribe to subjects through `subscriptions`; subscribers are the observers notified when new material appears.
- Favorites are stored per user in `material_favorites`; `materials.contador_favoritos` is a denormalized counter and `materials.es_favorito` is a legacy global flag.
- Thematic tags are a separate catalog. New materials also reference a first-class `categories` row through `materials.category_id`; the legacy comma-separated `materials.categories` text field is retained.
- Gamification stores XP on `users`, rank definitions in `ranks`, per-user badges in `user_badges`, follows in `user_subscriptions`, reads in `material_reads` and page-level reading progress in `reading_backlog`.

### Table groups

| Group | Tables |
|---|---|
| Identity and access | `roles`, `users` |
| Academic structure | `careers`, `career_years`, `subjects`, `subject_professors` |
| Materials | `categories`, `materials`, `material_subjects` |
| Student / subject relationship | `subscriptions` |
| Engagement | `material_favorites`, `thematic_tags`, `material_reads`, `reading_backlog` |
| Gamification | `ranks`, `user_badges`, `user_subscriptions`, `reading_streaks` |
| Notifications and traceability | `notifications`, `audit_logs` |

### Important modeling decisions

1. **`subjects.profesor_id` is a cached primary professor.**
   The authoritative many-to-many assignment is `subject_professors`. `subjects.profesor_id` is kept for backwards compatibility and quick display; the repository synchronizes it to the first assigned professor.

2. **`material_favorites` is authoritative for per-user favorites.**
   `materials.es_favorito` is a legacy/global flag, not the current user's state. `materials.contador_favoritos` is maintained as a cached count.

3. **`audit_logs.registro_id` is polymorphic.**
   It can point to a user, subject, material, role, career or career year. Because the target table varies, there is deliberately no foreign key on this column.

4. **`materials.file_hash` is unique but nullable.**
   The SHA-256 hash prevents duplicate uploads while a material is active. When a material is canceled or rejected, file fields are cleared, allowing the same file to be uploaded again later.

5. **`thematic_tags` does not enforce material references.**
   Tags are a moderated vocabulary. A material's `categories` field is plain text (a comma-separated list), so deleting a tag does not rewrite existing material text.

6. **No database-level role check exists for `subject_professors`.**
   The database guarantees that `profesor_id` references a real user, but the application is responsible for checking that the user has the `Profesor` role.

7. **Ranks are keyed by `rank_id`, not `level`.**
   The PRD names the rank level concept `level`; the implemented schema uses `ranks.rank_id` (1–9) and `users.rank_level` as the FK. Rank titles and XP floors are seeded by `init.sql` and must stay in sync with `frontend/img/profile_pictures/<title>.png`.

8. **`reading_backlog` doubles as reading progress.**
   `current_page`, `total_pages` and `status` persist the last page for reopening the viewer. Reaching the final page inserts into `material_reads`, removes the backlog row and preserves XP after an unread toggle.

9. **`material_subjects.is_mandatory` is per association.**
   The same material can be mandatory in one subject and optional in another; the API exposes a material-level `isMandatory` as the OR of its approved associations.

### Reading the cardinalities

- `||--o{` means **exactly one to zero or more**.
- `|o--o{` means **zero or one to zero or more** and is used for nullable foreign keys.
- `PK, FK` indicates a column that is both part of the primary key and a foreign key.

## 4. Table Dictionary

> `yes*` marks `created_at` columns whose DDL omits `NOT NULL`. Their effective nullability depends on the server: MySQL 8 with `explicit_defaults_for_timestamp=ON` permits `NULL`, while MariaDB defaults those `TIMESTAMP` columns to `NOT NULL` unless the same variable is enabled. The application always relies on the `CURRENT_TIMESTAMP` default. `audit_logs.timestamp` is explicitly `NOT NULL`.

### 4.1 `roles`

**Purpose:** Role catalog used for authorization (`Superadmin`, `Profesor`, `Alumno`).

| Column | Type | Null | Default | Key / constraint | Description |
|---|---|---|---|---|---|
| `id` | `INT` | no | auto increment | PK | Role identifier. |
| `nombre` | `VARCHAR(50)` | no | — | UNIQUE | Role name. |
| `descripcion` | `VARCHAR(255)` | yes | `NULL` | — | Human-readable role description. |

**Seeded roles:** `Superadmin` (1), `Profesor` (2), `Alumno` (3).

**Note:** Roles are seeded by `init.sql`; there is no public role-creation endpoint.

- `Rechazado`: a pending student upload rejected by a professor; file fields are cleared.

**Type values**

`PDF`, `EPUB`, `Word`, `Presentacion`, `Link_Drive`, `Youtube`, `Repositorio`.

**Indexes:** `autor_id`; unique `file_hash`; application queries also filter by `estado`, `tipo`, and title.

**File storage:** `url_or_path` and `portada` are typically relative paths under `uploads/`, but external links use the full URL. Storage mode is configured by `FILES_MODE` (`local` or `cloud`).

### 4.8 `material_subjects`

**Purpose:** Many-to-many classification of materials into subjects, including per-subject moderation state.

| Column | Type | Null | Default | Key / constraint | Description |
|---|---|---|---|---|---|
| `material_id` | `INT` | no | — | PK, FK → `materials.id`, `ON DELETE CASCADE` | Material. |
| `subject_id` | `INT` | no | — | PK, FK → `subjects.id`, `ON DELETE CASCADE` | Subject. |
| `estado_aprobacion` | `ENUM('Aprobado','Pendiente')` | no | `'Pendiente'` | — | Moderation state for this material-subject pair. |
| `is_mandatory` | `TINYINT(1)` | no | `0` | — | Professor-controlled mandatory flag for this subject. |

**Primary key:** composite `(material_id, subject_id)`.

**Behavior**

- Professor uploads are inserted as `Aprobado`.
- Student uploads are inserted as `Pendiente`.
- Catalog queries require **both** `materials.estado = 'Aprobado'` and `material_subjects.estado_aprobacion = 'Aprobado'`.
- A material can be approved for one subject while still pending in another. A student duplicate of an already-approved material adds a `Pendiente` association without changing the material's global `Aprobado` state.

**Indexes:** `subject_id`; composite PK covers `material_id` lookups.

### 4.9 `subscriptions`

**Purpose:** Immutable business-operation trail. Used by the admin audit screens.

### 4.13 `notifications`

**Purpose:** In-app notifications for students when a professor publishes or associates a material in a subject they follow.

| Column | Type | Null | Default | Key / constraint | Description |
|---|---|---|---|---|---|
| `id` | `INT` | no | auto increment | PK | Notification identifier. |
| `usuario_id` | `INT` | no | — | FK → `users.id`, `ON DELETE CASCADE`, index | Recipient. |
| `actor_id` | `INT` | yes | `NULL` | FK → `users.id`, `ON DELETE SET NULL` | User whose action triggered the notification. |
| `subject_id` | `INT` | yes | `NULL` | FK → `subjects.id`, `ON DELETE CASCADE` | Subject that originated a material notification. |
| `material_id` | `INT` | yes | `NULL` | FK → `materials.id`, `ON DELETE CASCADE` | Material notification target. |
| `type` | `VARCHAR(50)` | no | `'material'` | — | `material`, `favorite`, `follow`, `badge`, `streak`, etc. |

## 5. State Machines and Lifecycles

### 5.1 Account lifecycle

```mermaid
stateDiagram-v2
    [*] --> PendienteVerificacion: register()
    PendienteVerificacion --> Activo: verify / activate
    Activo --> Baneado: admin ban
    Baneado --> Activo: admin unban
    Activo --> Inactivo: admin soft delete
    Baneado --> Inactivo: admin soft delete
    PendienteVerificacion --> Inactivo: admin soft delete
    Inactivo --> [*]
```

The admin ban/unban endpoints do not restrict the starting state: `ban` can set any existing account to `Baneado`, and `unban` can set any existing account (including `Inactivo`) back to `Activo`.

### 5.2 Material and association lifecycle

```mermaid
stateDiagram-v2
    [*] --> Pendiente: student upload
    [*] --> Aprobado: professor upload / admin batch
    Pendiente --> Aprobado: professor approves association
    Pendiente --> Rechazado: last pending association rejected
    Pendiente --> Cancelado: author cancels
    Rechazado --> [*]
    Cancelado --> [*]
```

For a material with several subjects, `materials.estado` and each `material_subjects.estado_aprobacion` can differ:

- Student upload: material `Pendiente`; every association `Pendiente`.
- Professor approves one subject: that association becomes `Aprobado`; the material becomes `Aprobado`.
- Professor rejects one subject: that association is deleted. If other associations remain, the material stays visible for those subjects. If no associations remain and the material was `Pendiente`, the material becomes `Rechazado` and its file fields are cleared. If the material was already `Aprobado`, it remains `Aprobado` with no associations and its files are kept.
- Cancel: only `Pendiente` materials can be canceled by the author. The material becomes `Cancelado`, file fields are cleared, and all associations are deleted.

### 5.3 Subscription lifecycle

```mermaid
stateDiagram-v2
    [*] --> Suscrito: subscribe
    Suscrito --> Baneado: professor/admin ban
    Suscrito --> [*]: unsubscribe (row deleted)
    Baneado --> [*]: row removed outside the student flow
```

The service refuses to subscribe a student whose row is `Baneado`; the ban persists until the row is removed or changed outside the normal student flow.

## 6. Derived Counts and Catalog Semantics

The repositories compute these values rather than storing them:

| Value | Meaning |
|---|---|
| `career.totalMaterias` | Number of subjects in the career. |
| `career.totalMateriales` | Number of distinct material ids in approved associations within the career; the query does not additionally filter `materials.estado`. |
| `career_year.totalMaterias` | Number of subjects in that year. |
| `career_year.totalMateriales` | Number of distinct material ids in approved associations for that year; no additional `materials.estado` filter. |
| `subject.totalMateriales` | Number of associations with `estado_aprobacion = 'Aprobado'`; no additional `materials.estado` filter. |
| `material.contadorFavoritos` | Stored counter, updated on favorite toggle. |
| `material.esFavorito` | Whether the current authenticated user has a `material_favorites` row. |

Catalog visibility rules:

1. **Global catalog:** `materials.estado = 'Aprobado'`. An approved material remains visible globally even if it has no subject associations, so professors can find and re-associate it.
2. **Subject page:** `materials.estado = 'Aprobado'` **and** a matching `material_subjects` row with `estado_aprobacion = 'Aprobado'`.
3. **Author profile:** approved materials authored by that user.

|---|---|

## 8. Integrity Rules and Application Responsibilities

| Rule | Enforced by |
|---|---|
| Email uniqueness | Database unique index + `AuthService`. |
| Role existence | FK `users.role_id`. |
| Only users with role `Profesor` should be assigned to subjects | Application checks on subject create/update and professor request; `confirm-association` with an arbitrary `profesorId` only relies on the user FK and does not re-check the role. |
| A professor can only review materials in subjects they teach | Application (`Subject.hasProfessor`). |
| A student can only upload three pending materials | Application (`MaterialService.uploadOrSuggestMaterial` / `assertPendingLimit`). |
| A student cannot subscribe to a banned subscription | Application (`SubscriptionService.subscribe`). |
| A professor can only ban observers of subjects they teach | Application (`SubscriptionService.banStudent`). |
| Duplicate active files are not stored twice | Database unique `file_hash` + application duplicate flow. |
| One favorite per user/material | Database unique constraint. |
| One notification per user/type/material/subject | Database unique constraint. |
| Tags are unique per `(nombre, categoria)` | Database unique constraint. |
| One read/backlog row per user/material | Database composite primary key. |
| A user cannot follow themselves | Application (`GamificationService.follow/unfollow`). |
| Rank picture requires the matching rank | Application (`GamificationService.listProfilePictures` / `updateProfile`). |
| Audit rows are append-only | Application; no update/delete endpoint exists. |
| Soft-deleting a user preserves history | Application sets `estado = 'Inactivo'`; hard deletion cascades. |

### Application-only invariants

- `subjects.profesor_id` should equal one of the professors in `subject_professors`; the repository synchronizes it after assignment changes.
- `materials.contador_favoritos` should equal the number of rows in `material_favorites` for that material; the favorite flow increments/decrements it without an explicit transaction, and the API returns a fresh count.
- `materials.es_favorito` is not kept in sync with per-user favorites and should be treated as legacy.
- A material with no `material_subjects` rows is not shown on subject pages, but it remains visible in the global catalog when its `estado` is `Aprobado`.

## 9. Deletion Behavior Summary

| Deletion | Effect |
|---|---|
| Delete a role | Blocked while users reference it (no cascade). |
| Delete a career | Deletes its `career_years`; subjects in those years get `career_year_id = NULL`. |
| Delete a career year | Subjects get `career_year_id = NULL`. |
| Delete a subject | Deletes its `subject_professors`, `material_subjects`, `subscriptions`, and `notifications`; materials remain. |
| Delete a user (hard) | Deletes authored materials, subscriptions, favorites and notifications; audit logs and tags keep `NULL` actor/creator; subject assignments and cached `profesor_id` are cleared. |
| Delete a material | Deletes its `material_subjects`, `material_favorites`, and `notifications`; files are removed by the application. |
| Delete a subscription | Notifications already created remain. |
| Delete a tag | Materials keep their text categories. |

The public API avoids hard-deleting users: `DELETE /api/auth/users/:id` sets `estado = 'Inactivo'`.

## 10. Seed Data Summary

`init.sql` seeds:

- 3 roles.
- 9 ranks (0–7000 XP thresholds).
- 23 material categories.
- 3 users (admin, professor, student).
- 1 career with 3 year levels.
- 23 subjects:
  - Year 1: 8 subjects.
  - Year 2: 8 subjects.
  - Year 3: 7 subjects.
- No `subject_professors` assignments; all subjects start with `profesor_id = NULL`.
- No materials, subject subscriptions, favorites, reads, backlog, follows, streaks, badges, tags, notifications or audit rows.

This means a fresh database has a populated academic catalog but no teaching assignments. An administrator must create/assign professors before professor-specific flows can return meaningful data.
