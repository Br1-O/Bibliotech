# Bibliotech — Class Diagram and Component Model

**Project:** Bibliotech  
**Document:** Domain, application, infrastructure, adapter and frontend class model  
**Generated:** 2026-10-29  
**Sources of truth:** `bibliotech/backend/domain/`, `bibliotech/backend/application/`, `bibliotech/backend/infrastructure/`, `bibliotech/backend/controllers/`, `bibliotech/backend/routes/`, `bibliotech/backend/middleware/`, `bibliotech/backend/validator/`, `bibliotech/frontend/js/`

> The backend is implemented with CommonJS modules. Classes are used for domain entities, ports, services, repositories, validators, middleware helpers and frontend components. Express controllers and routes are factory functions/modules; they are shown with the `<<factory>>` or `<<router>>` stereotype. The diagrams are split by layer to keep each view readable.

---

## 1. Architectural Overview

Bibliotech follows a **hexagonal / ports-and-adapters** structure:

| Layer | Responsibility | Main files |
|---|---|---|
| Domain | Business entities, observer pattern, repository contracts | `domain/entities/`, `domain/observers/`, `domain/ports/` |
| Application | Use cases, authorization, moderation, audit and notification orchestration | `application/services/` |
| Infrastructure | MariaDB repositories, email transport, file helpers, dependency container | `infrastructure/`, `utils/` |
| Input adapters | Express routes, controllers, middleware, validators, view routes | `routes/`, `controllers/`, `middleware/`, `validator/` |
| Frontend | Page controllers, API client, Web Components, i18n, validation | `frontend/js/` |

### Dependency direction

```mermaid
flowchart LR
    FE["Frontend modules"] --> HTTP["Express routes"]
    HTTP --> MW["Middleware"]
    HTTP --> CTRL["Controllers"]
    CTRL --> SVC["Application services"]
    SVC --> ENT["Domain entities"]
    SVC --> PORTS["Repository ports"]
    REPO["MariaDB repositories"] -. implements .-> PORTS
    SVC --> AUDIT["AuditLogService"]
    SVC --> MAIL["MailerService"]
    CTRL --> REPO
    DI["buildContainer"] --> REPO
    DI --> SVC
```

**Key rule:** application services depend on domain ports, never on concrete MariaDB classes. Concrete repositories are injected by `infrastructure/container.js`. A few read-only controllers also use repositories directly for list operations, which is a pragmatic shortcut rather than a violation of the domain flow.

**Notes**

- `Subject` also inherits from `Observable`; the inheritance is shown in the observer diagram.
- `Material.TIPOS` is a static list: `PDF`, `EPUB`, `Word`, `Presentacion`, `Link_Drive`, `Youtube`, `Repositorio`.
- `Material.cancelUpload()` only enforces the “pending only” rule and changes the in-memory state; persistence is completed by `MaterialService` and `MaterialRepository`.
- `Subscription.ban()` and `Subscription.reactivate()` change the in-memory state; persistence is completed by the repository/service.
- `User.toSafeJSON()` removes `password`, reset token data and verification token data before API serialization.
- There is no domain entity class for notifications, ranks, categories, reads, backlog, follows, streaks or badges. `GamificationService` and `MariaDBGamificationRepository` use plain row objects and map them explicitly.
- `Material.isMandatory`, `categoryId`, `categorySlug` and `uploadedBy` are attached by `MariaDBMaterialRepository` when loading associations; they are not necessarily stored on the domain entity at creation time.
- `User.profilePicture` must be a default picture or a rank picture the user has unlocked; `GamificationService.updateProfile()` enforces this against `ranks`.

### 2.2 Observer pattern

```mermaid
classDiagram
    class Observable {
        +Observer[] observers
        +attach(observer)
        +detach(observer)
        +object[] notify(event, payload)
    }

    class Subject {
        +int id
        +string nombre
        +int profesorId
        +object[] profesores
        +bool activa
        +int[] profesorIds
        +bool hasProfessor(id)
        +object[] notifyObservers(material)
    }

    class StudentObserver {
        +int alumnoId
        +string email
        +int materiaId
        +string lang
        +object[] notifications
        +object update(event, payload)
    }

    Observable <|-- Subject
    Subject "1" o-- "*" StudentObserver : observers
    Subject ..> StudentObserver : update("MATERIAL_PUBLICADO", payload)
```

**Runtime behavior**

1. `MaterialService.notifyObservers(subject, material)` loads all `Suscrito` subscribers from `subscriptionRepository.getObservers(subject.id)`.
2. It creates a transient `Subject` instance and attaches one `StudentObserver` per subscriber row.
3. `Subject.notifyObservers(material)` calls `notify('MATERIAL_PUBLICADO', ...)`.
4. Each `StudentObserver.update()` returns an in-memory notification object.
5. The service separately persists notifications through `NotificationRepository.createForSubscribers()`. Persistence failure is logged but does not abort the material upload/approval.

**Design consequence:** the Observer pattern is used as the domain notification mechanism, while the `notifications` table is the durable inbox. In-memory observer notifications are ephemeral and are not returned by the API.

### Important service rules

**`AuthService`**

- Registration always creates an `Alumno` account in `PendienteVerificacion`.
- Professor creation is an admin action and creates an `Activo` professor.
- Login rejects `PendienteVerificacion`, `Inactivo` and `Baneado`.
- Password-reset requests are deliberately uniform to avoid account enumeration.
- Reset tokens are hashed in the database and expire.
- `toSafeJSON()` is used for API responses.

**`SubjectService`**

- `resolveProfessorIds()` accepts `profesorId` or `profesorIds`, verifies each user exists and has the `Profesor` role. This check is used by create/update; `confirmAssociation()` does not re-check the role when an admin supplies `profesorId`.
- `createSubject` can create a subject with no professor; it always starts with `estadoAsociacion = 'Activa'`. A later professor `requestAssociation` changes it to `'Pendiente'` until an admin confirms.
- `requestAssociation` adds the professor and marks the subject `Pendiente`.
- `confirmAssociation` adds the professor (if supplied) and marks the subject `Activa`.
- `rejectAssociation` removes all professors and clears the cached `profesor_id`; it sets `estadoAsociacion = 'Pendiente'` only when the subject was already pending, so an active subject can remain `Activa` while unassigned.

**`MaterialService`**

- Professor uploads are auto-approved and become visible immediately.
- Student uploads are pending and limited to three per student.
- Duplicate file hash:
  - Professor: associates the existing material with the selected subjects as `Aprobado`, without changing the material's global state.
  - Student: associates the existing material as pending.
- `assertCanManage()` allows:
  - the author at the service level, regardless of role (the `PUT /api/materials/:id` route itself allows only Professor/Superadmin);
  - a Superadmin, but only for a material whose author is an `Alumno` (because the non-student-author check runs first);
  - a professor, but only for a student suggestion in a subject the professor teaches.
- No caller can edit another professor's or administrator's material except its original author.
- `approveMaterial` and `rejectMaterial` require the caller to be a professor of the target subject (or admin).
- `delete(materialId, ctx, subjectId)` with a `subjectId` removes only that association; without one it deletes globally and is admin-only at the route level.
- Favorites are toggled with a read-then-write sequence (no explicit DB transaction) and return `{ favorited, contadorFavoritos }`; the returned count comes from a fresh `COUNT(*)`.

**`GamificationService`**

- A read is stored in `material_reads`; first insert adds `100` XP and recalculates `users.rank_level` from `ranks.min_xp`. Unmarking removes the read but never subtracts XP.
- Badges: `hello_world` (first read), `first_commit` (first upload), `stack_overflow` (10 uploads), `shared_pointer` (5 followers), `array_5` (5 following), `linter_clean` (5 reads), `code_reviewer` (10 favorites), `full_stack_reader` (rank ≥ 5), `early_return` (read/upload between 05:00–09:59), `overtime` (read/upload between 00:00–04:59).
- Reading progress is upserted in `reading_backlog`; `total_pages` falls back to `materials.pages`; `current_page >= total_pages` moves the item to `material_reads` and removes the backlog row.
- Follow notifications are inserted for the target's followers on read; badge unlocks create `badge` notifications.
- Profile picture updates reject locked rank images (`errors.profilePictureLocked`).
- Heartbeat sessions are keyed `user:material`; 300 accumulated active seconds qualify the daily streak. Sessions expire after 300 seconds without a heartbeat, and `resetHeartbeat()` clears one explicitly.

**`SubscriptionService`**

- Banning requires the caller to teach the subject (or be admin).
- Banned students cannot re-subscribe while the banned row exists.
- `getObservers` returns only `Suscrito` rows. The service does not check ownership for viewing the list; the route only requires Professor/Admin.

### Role string constants

`Role.SUPERADMIN = 'Superadmin'`, `Role.PROFESOR = 'Profesor'`, `Role.ALUMNO = 'Alumno'`. These values match the database seed and the middleware authorization checks.

**Middleware**

| Component | Responsibility |
|---|---|
| `verifyToken` | Requires `Authorization: Bearer <JWT>`, verifies the signature and attaches `req.usuarioId`/`req.rol`. It does not re-query the database, so an already-issued token remains valid until expiry even if the user is later banned or soft-deleted. |
| `optionalAuth` | Attempts to decode a token; if absent/invalid, continues as anonymous. Used to add `esFavorito` to catalog responses. |
| `requireRole(...roles)` | Returns 403 unless the authenticated user's role name is in the allowed list. |
| `languageMiddleware` | Resolves `lang`, `x-language` or `Accept-Language` and attaches a request-local translator/language manager. |
| `errorMiddleware` | Converts `AppError`, validation errors and unexpected errors into localized JSON responses. |
| `uploadRateLimitMiddleware` | Limits upload requests per user/IP (default 50 per minute). |
| `rateLimitMiddleware` | Legacy duplicate upload limiter (5/minute, fixed message). It is not mounted; the server uses `uploadRateLimitMiddleware` instead. |

**Route composition:** `routes/*.js` are factories that receive the DI container, create their controller, and register endpoints. `server.js` mounts the API routers under `/api` (including `engagementRoutes` and `streakRoutes`), view routes at the root, static assets and uploads. `engagementRoutes` applies `verifyToken` per route (a router-level guard previously swallowed every `/api` path).

### Frontend navigation and access

- Page access is controlled client-side by `authHelper` and each page controller. There is no server-side page guard: a user can load a dashboard HTML file, but API calls still enforce roles.
- `authHelper.panelRoute()` sends `Superadmin` to `/admin`, `Profesor` to `/profesor`, and others to `/alumno`.
- `apiService` clears the session and redirects to `/login` on 401.
- The teacher dashboard filters subjects client-side with `subject.isSubjectProfessor`/`profesorIds`, matching the backend's `subject_professors`.

## 7. Design Patterns and Cross-Cutting Concerns

| Pattern | Where | Purpose |
|---|---|---|
| Hexagonal architecture | Whole backend | Isolate domain/application from MariaDB and Express. |
| Repository | `domain/ports` + `infrastructure/repositories` | Swappable persistence. |
| Dependency injection | `infrastructure/container.js` | Build the object graph once; controllers/routes receive it. |
| Observer | `Observable`, `Subject`, `StudentObserver` | Notify subscribed students about published material. |
| Chain of responsibility / specification | `ValidationHandler` + rules | Compose field validations. |
| Factory | Controllers, routes, `buildContainer` | Create configured request handlers/routers. |
| Strategy-like role checks | `requireRole`, service guards | Different behavior for `Superadmin`, `Profesor`, `Alumno`. |
| MVC-ish | Routes/controllers → services → entities | HTTP adaptation separated from use cases. |
| Web Components | `Navbar`, `Button`, `PasswordField`, `TagInput` | Reusable UI elements. |
| i18n observer | `LanguageManager` | Re-render/translate on language change. |
| Client-side pagination | `Pagination` | The API returns full result arrays; the frontend paginates. |

### Cross-cutting rules

| Concern | Implementation |
|---|---|
| Authentication | JWT bearer token, 2-hour expiry, `verifyToken`. |
| Authorization | `requireRole` at route level plus ownership checks in services. |
| Localization | `LanguageManager` + `req.lang`/translator; API messages are translation keys resolved by `ok()`/error middleware. |
| Audit | `AuditLogService.record()` called by write services. |
| Error handling | `AppError` and `ValidationError`; localized `{ message, code, errors }`. |
| File handling | `multer` → `fileHelper` / configured storage; SHA-256 duplicate detection. |
| Rate limiting | Upload limiter (50/minute by user/IP, overridable via env); the legacy `rateLimitMiddleware` duplicate is not mounted. |
| Security | bcrypt password hashes, hashed tokens, parameterized SQL via `mysql2`, safe JSON serialization. |

### Known implementation details / caveats

1. **Read-only controllers may bypass services.** Some listing endpoints call repositories directly to avoid duplicating filter logic. This is intentional and documented in the route reference.
2. **`ThematicTagRepositoryInterface` does not extend the base port.** Its methods throw directly; this does not affect the MariaDB implementation.
3. **`subjects.profesor_id` is denormalized.** Always treat `subject_professors` as the source of truth.
4. **Files are not automatically deleted from storage by the database.** The service calls `fileHelper`/deletes paths; a DB cascade cannot remove disk files.
5. **In-memory observer notifications are not durable.** Only rows written to `notifications` survive a request.
6. **The frontend is not a single-page application.** Each page has its own controller module and loads shared components/scripts.
7. **Client-side pagination is the current behavior.** API endpoints do not expose page/pageSize parameters except the favorites repository's internal `limit`/`offset` support, which the controller passes through without validation.
8. **Role names are exact strings.** `'Superadmin'`, `'Profesor'`, `'Alumno'`; translations only affect display, not authorization.
9. **Duplicate uploads can leave an orphan file.** A professor/student duplicate hash reuses the existing material, but the controller only cleans newly written files on error; the duplicate upload succeeds and leaves the new file on disk.
