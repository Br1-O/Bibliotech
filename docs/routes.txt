## 1. How to Read This Document

Each endpoint entry contains:

- **Access:** public, optional authentication, any authenticated user, or role-restricted.
- **Input:** path/query/body/file fields actually read by the controller.
- **Success:** status and the main response fields. Response messages are localized text, not translation keys.
- **Errors and notes:** expected error statuses and important implementation behavior.

### 2.2 Roles

| Role name in JWT/DB | Meaning in this document |
|---|---|
| `Superadmin` | Administrator. Referred to as “Admin” in tables. |
| `Profesor` | Professor. |
| `Alumno` | Student. |

### 2.3 Authentication

- Format: `Authorization: Bearer <JWT>`.
- JWT payload: `{ id, role }`; default expiry **2 hours** (`JWT_EXPIRES`).
- `verifyToken` only verifies the JWT signature and attaches `req.usuarioId` / `req.rol`. It does **not** re-query the user or re-check `estado`. A banned/deleted user with an existing JWT can keep using it until expiry; login itself rejects those accounts.
- `optionalAuth` attaches identity if a valid token is present and otherwise continues anonymously. An invalid token is silently ignored.
- Missing token → `401 { message }`.
- Wrong role → `403 { message }`.
- Public routes do not require a token; sending one may still enrich the response (for example, `esFavorito`).

### 2.4 Localization

Language resolution order:

1. `?lang=es|en`
2. `x-language` header
3. first value of `Accept-Language`
4. `DEFAULT_LANGUAGE` (default `es`)

Unknown languages fall back to `DEFAULT_LANGUAGE`. Controllers return translation keys; `ok()` and the error middleware resolve them into human-readable messages.

### 2.5 Response envelopes

Successful responses have no universal `data` wrapper. Examples:

```json
{ "subjects": [ ... ] }
{ "materials": [ ... ] }
{ "message": "Material subido correctamente.", "material": { ... } }
```

Errors:

```json
{ "message": "No autorizado.", "code": "errors.unauthorized" }
```

Validation errors:

```json
{
  "message": "Datos invalidos.",
  "errors": ["El campo Titulo es obligatorio."],
  "fields": { "titulo": "El campo Titulo es obligatorio." }
}
```

Multer size/type errors may return only `{ "message": "..." }`.

### 2.6 Status codes

| Status | Meaning |
|---|---|
| `200` | Success. |
| `201` | Resource created (or duplicate tag returned through the create endpoint). |
| `400` | Invalid token/code, missing required data in a few services, Multer file errors, thematic tag invalid. |
| `401` | Missing/invalid JWT. |
| `403` | Authenticated but role or ownership check failed; account blocked at login. |
| `404` | Resource not found. |
| `409` | Duplicate email, pending-upload limit, duplicate file hash. |
| `422` | Field/business validation error. |
| `429` | Upload rate limit exceeded. |
| `500` | Unexpected server/DB error. |

### 2.7 Naming

- Most JSON uses **camelCase** (`createdAt`, `profesorId`, `fileHash`, `estadoAsociacion`). Exceptions: `GET /api/subscriptions/mine` returns raw `alumno_id`, `materia_id` and `created_at` alongside camel aliases; thematic-tag read responses return `creadoPor`/`createdAt` as `null` because of a mapper mismatch.
- Database columns use **snake_case** (`created_at`, `profesor_id`, `file_hash`, `estado_asociacion`).
- Enum values preserve Spanish labels (`Aprobado`, `Pendiente`, `Cancelado`, `Rechazado`, `Suscrito`, `Baneado`, `Activa`, `Pendiente`).

### 2.8 Pagination, filtering and sorting

- The API does **not** implement page/pageSize for most endpoints.
- The frontend paginates client-side with `Pagination.DEFAULT_PAGE_SIZE = 6`.
- Exception: `GET /api/materials/favorites/mine` passes `limit` and `offset` query values to the repository; values are parsed internally without explicit validation.
- Lists are usually newest-first (`created_at DESC`) or alphabetically by career/year/subject.

### 2.9 Upload limits and storage

| Limit | Value |
|---|---|
| Max file size per file | 100 MB (`MAX_FILE_SIZE`) |
| Max files per multipart request | 220 |
| Batch item limit | 100 |
| Cover image max size | 5 MB |
| Cover extensions | `.jpg`, `.jpeg`, `.png`, `.webp`, `.gif` |
| Upload rate limit | 50 requests/minute per user/IP by default; disabled in `NODE_ENV=testing` |
| Local storage | `backend/uploads/`, served at `/uploads/...` |
| Cloud storage | Cloudinary when `FILES_MODE=cloud` |
| Duplicate detection | SHA-256 `file_hash`, unique per active material |

### 2.11 Audit labels

Audit rows store human-readable labels, for example:

`Alta Usuario`, `Verificacion Cuenta`, `Solicitud Reseteo Clave`, `Cambio Clave`, `Desbaneo Usuario`, `Baja Usuario`, `Alta Rol`, `Solicitud Materia`, `Alta Materia`, `Asociacion Materia`, `Modificacion Materia`, `Alta Carrera`, `Modificacion Carrera`, `Alta Anio`, `Modificacion Anio`, `Subida Material`, `Asociacion Material`, `Aprobacion Material`, `Modificacion Material`, `Desasociacion Material`, `Cancelacion Material`, `Borrado Material`, `Suscripcion Materia`, `Baneo Alumno`.

### 2.12 Route-matching notes

- Material special paths (`/global`, `/author/:id`, `/mine`, `/pending`, `/pending-review`, `/favorites/mine`) are declared **before** `/:id` routes, so they are not captured as IDs.
- `/api/materials/:id/subjects/:subjectId` is declared before `/api/materials/:id`; Express matches the longer path first.
- `/api/careers/years/:yearId` is a separate two-segment path and is not shadowed by `/api/careers/:id`.
- The bare `DELETE /api/materials/:id` route is admin-only, but the controller also accepts `?subjectId=` and will perform a subject-specific removal.

- `GET /api/profile/:id` is public but enriches `isFollowing`/`isSelf` when a token is supplied.
- XP is recalculated against `ranks.min_xp`; unmarking a read removes the read row but does not subtract XP.
- Streak sessions are held in memory, keyed by `user:material`, and expire after 300 seconds without a heartbeat.
- Rank pictures live at `/img/profile_pictures/<Rank Title>.png`; default pictures are `default-1.png` … `default-3.png`.
- Badge images live at `/img/badges/<badge_key>.png`.
- `GET /api/users/:id/backlog` returns `{ items: [{ materialId, currentPage, totalPages, status, progress, material }] }`.

## 4. Detailed Endpoint Reference

## 4.1 Authentication and Users

### 1. `POST /api/auth/register`

**Access:** Public.

**Input (JSON):**

| Field | Type | Required | Rules |
|---|---|---|---|
| `nombre` | string | yes | 2–50 characters. |
| `apellido` | string | yes | 2–50 characters. |
| `email` | string | yes | Valid email; unique; normalized to lowercase. |
| `password` | string | yes | Minimum 8 characters, at least one letter and one digit. |
| `passwordConfirm` | string | no | If supplied, must equal `password`. |

**Action:** Creates an `Alumno` in `PendienteVerificacion`, hashes the password with bcrypt, creates a hashed verification token (default 60 minutes), attempts to send an activation email, and writes audit `Alta Usuario`.

**Success:** `201`

```json
{
  "message": "Registro exitoso...",
  "user": { "id": 4, "nombre": "...", "email": "...", "estado": "PendienteVerificacion", "...": "..." },
  "devToken": "optional only outside production"
}
```

**Errors:** `409 validation.emailTaken`; `422` field validation; `500` missing `Alumno` role. Mail failure is logged but does not fail registration.

---

### 2. `POST /api/auth/verify-account`

**Access:** Public.

**Input:** body may contain `token` or `code`, and optionally `email`.
- If `email` and token/code are both supplied, the token must belong to that email.
- With only token/code, the token alone is used.

**Success:** `200 { "message": "Cuenta verificada..." }`

**Errors:** `400 errors.invalidToken` for missing, expired, already-used, or mismatched token.

**Action:** Sets `users.estado = 'Activo'`, clears the verification token, records `Verificacion Cuenta`.

---

### 3. `GET /api/auth/verify-account`

Same as #2, but reads `token`/`code`/`email` from query parameters.

---

### 4. `POST /api/auth/activate`

**Access:** Public.

**Input:** `{ "token": "..." }`.

**Success:** `200 { "message": "Cuenta verificada..." }`

**Errors:** `400 errors.invalidToken`.

---

### 5. `GET /api/auth/activate/:token`

Same as #4 with the token in the path.

---

### 6. `POST /api/auth/resend-verification`

**Access:** Public.

**Input:** `{ "email": "..." }` (required, valid email).

**Action:** If the account exists and is pending, generates a new token and sends a new email. Otherwise returns the same generic message.

**Success:** `200 { "message": "..." }`, plus `devToken` outside production.

**Errors:** `422` invalid email.

**Privacy:** Does not reveal whether the email exists.

---

### 7. `POST /api/auth/login`

**Access:** Public.

**Input:**

| Field | Required |
|---|---|
| `email` | yes |
| `password` | yes |

**Action:** Finds user by normalized email, compares bcrypt hash, checks `estado`, signs JWT `{ id, role }` with 2-hour default expiry.

**Success:** `200`

```json
{
  "message": "Sesion iniciada...",
  "token": "eyJ...",
  "user": { "id": 2, "roleNombre": "Profesor", "nombreCompleto": "...", "...": "..." }
}
```

**Errors:**

- `422` missing email/password.
- `401 errors.invalidCredentials` for unknown email or wrong password.
- `403 errors.accountNotVerified` for `PendienteVerificacion`.
- `403 errors.accountDisabled` for `Inactivo`/`Baneado`.

**Audit:** None on login.

---

### 8. `POST /api/auth/forgot-password`

**Access:** Public.

**Input:** `{ "email": "..." }`.

**Action:** Always returns a generic response. If the user exists, creates a hashed reset token (default 60 minutes), sends the recovery email, and records `Solicitud Reseteo Clave`. Audit failure does not block.

**Success:** `200`

```json
{ "message": "...", "expiresInMinutes": 60, "devToken": "optional outside production" }
```

If the email does not exist, only the generic `message` is returned (no `expiresInMinutes`/`devToken`).

**Note:** The service does not filter by `users.estado`; an inactive or banned account can still receive a reset token, although login remains blocked.

**Errors:** `422` invalid email.

---

### 9. `GET /api/auth/reset-password/:token/validate`

**Access:** Public.

**Input:** token in path.

**Success:** `200 { "valid": true|false }`

**Notes:** Does not consume the token. `false` for missing/expired/unknown tokens. No error response for an invalid token.

---

### 10. `POST /api/auth/reset-password`

**Access:** Public.

**Input:**

| Field | Required | Rules |
|---|---|---|
| `token` or `code` | yes | Must map to a non-expired reset token. |
| `password` | yes | Minimum 8, letter + digit. |
| `passwordConfirm` | no | If supplied, must match. |

**Action:** Updates the bcrypt password, clears reset token fields, records `Cambio Clave`.

**Success:** `200 { "message": "Contrasena actualizada..." }`

**Errors:** `422` validation; `400 errors.invalidToken` for unknown/expired token.

---

### 11. `PUT /api/auth/password`

**Access:** Any authenticated user.

**Input (JSON):**

| Field | Required | Rules |
|---|---|---|
| `currentPassword` | yes | Must match the stored bcrypt hash. |
| `password` | yes | Minimum 8, letter + digit. |
| `passwordConfirm` | no | If supplied, must match `password`. |

**Action:** Verifies the current password, hashes the new one with bcrypt, updates `users.password` and records `Cambio Clave`.

**Success:** `200 { "message": "Contrasena actualizada..." }`

**Errors:** `422 validation.currentPassword` for a wrong current password; `422` for missing or invalid new password.

---

### 12. `GET /api/auth/roles`

**Access:** Public.

**Success:** `200 { "roles": [ { "id": 1, "nombre": "Superadmin", "descripcion": "..." }, ... ] }`

---

### 13. `GET /api/auth/me`

**Access:** Any authenticated user.

**Success:** `200 { "user": { ...safe user... } }`

**Errors:** `401`; `404` if the user no longer exists.

---

### 14. `POST /api/auth/professors`

**Access:** Superadmin.

**Input:** Same fields as registration (`nombre`, `apellido`, `email`, `password`, optional `passwordConfirm`).

**Action:** Creates an account with role `Profesor` and default state `Activo`; hashes the password; records `Alta Usuario` with the admin as actor.

**Success:** `201 { "message": "...", "user": { ... } }`

**Errors:** `409` duplicate email; `422` validation.

**Note:** The professor is not assigned to any subject by this endpoint; use subject creation/association. Unlike registration/login, this path does not trim or lowercase the submitted email before insert.

---

### 15. `GET /api/auth/users`

**Access:** Superadmin.

**Success:** `200 { "users": [ ...safe users... ] }`

**Note:** Returns all users; passwords/tokens are omitted by the repository mapping.

---

### 16. `PUT /api/auth/users/:id/ban`

**Access:** Superadmin.

**Input:** none (path id).

**Action:** Sets `users.estado = 'Baneado'`; records `Baneo Alumno` (even for non-students).

**Success:** `200 { "message": "Usuario baneado..." }`

**Errors:** `404` user not found.

**Note:** There is no target-role or self-protection check; any existing account, including a Superadmin or the caller, can be banned. Existing JWTs remain usable until expiry.

---

### 17. `PUT /api/auth/users/:id/unban`

**Access:** Superadmin.

**Action:** Sets `users.estado = 'Activo'`; records `Desbaneo Usuario`.

**Success:** `200 { "message": "Usuario desbaneado..." }`

**Errors:** `404` user not found.

---

### 18. `DELETE /api/auth/users/:id`

**Access:** Superadmin.

**Action:** Soft delete: `users.estado = 'Inactivo'`; records `Baja Usuario`. The row is not deleted.

**Success:** `200 { "message": "Usuario eliminado..." }`

**Errors:** `404` user not found.

**Note:** Existing JWTs remain usable until expiry because `verifyToken` does not re-check state.

### 39. `POST /api/materials/upload`

**Access:** `Alumno`, `Profesor` (Superadmin cannot use this route; use batch upload).

**Content type:** `multipart/form-data`.

**Fields:**

| Field | Required | Rules |
|---|---|---|
| `titulo` | yes | 2–150 characters (frontend asks for 3+). |
| `descripcion` | no | Stored as trimmed text; empty becomes `NULL`. |
| `pages` | no | Positive integer page count; used by the viewer to auto-complete reading progress. |
| `tipo` | conditionally | One of the 7 types; inferred from file/URL if omitted. |
| `archivo` | conditionally | Required when using a file type; max 100 MB. |
| `urlOrPath` | conditionally | Required when using a link type; validated by type. |
| `subjects` | yes | Comma-separated or repeated subject ids; at least one. |
| `categories` | no | Comma-separated or repeated tag text. |
| `portada` | no | Image; max 5 MB; valid image extension. |

**At least one** of `archivo` or `urlOrPath` must be effective after type inference.

**Action:**

- Professor: all selected subjects must be taught by the caller; material is saved as `Aprobado`; associations are `Aprobado`; subscribers are notified; audit `Subida Material`.
- Student: material is saved as `Pendiente`; associations are `Pendiente`; max 3 pending materials; no notification.
- Duplicate SHA-256:
  - Professor: existing material is associated to the subjects as `Aprobado`; subscribers notified; audit `Asociacion Material`; message says duplicate. The existing material's own `estado` is **not** changed by this path, so a pending duplicate does not become globally approved automatically.
  - Student: existing material is associated as `Pendiente`; pending limit applies; audit `Asociacion Material`. If the existing material is already `Aprobado`, it stays globally visible; only this subject association is pending.
- Categories are also inserted into `thematic_tags` with category `general`, ignoring failures for duplicates/banned tags.

**Success:** `201 { "message": "...", "material": { ... } }`

**Errors:**

| Status | Condition |
|---|---|
| `422` | Missing title/subject/file/link; invalid file/link/cover; title length. |
| `403` | Professor does not teach one of the selected subjects. |
| `409` | Student already has 3 pending materials. |
| `429` | Upload rate limit exceeded. |
| `400` | Multer file size/type errors. |

**Cleanup:** Newly written local files are deleted if the request fails after Multer. On a successful duplicate-hash upload, the newly uploaded file/cover is **not** removed; it remains as an orphan in storage (local or cloud) because the duplicate branch returns success without cleanup.

---

### 40. `POST /api/materials/batch`

**Access:** Superadmin.

**Content type:** `multipart/form-data`.

**Fields:**

| Field | Meaning |
|---|---|
| `archivo_0`, `archivo_1`, ... or `archivos` | Files; indexed names preserve pairing. |
| `portada_0`, ... or `portadas` | Optional covers. |
| `metadata` | JSON array of objects such as `[{ "titulo": "...", "pages": 120 }]`. |
| `links` | Newline-separated `Titulo|URL[|pages]`, or an array/objects (`{titulo,url,pages}`). |
| `categories` | Comma-separated tags applied to all items. |

**Limits:** 1–100 total items; max 220 uploaded files; 100 MB per file.

**Action:** Validates each file/link type, creates materials as `Aprobado` **without subject associations**, inserts submitted categories into `thematic_tags` (ignoring duplicate/banned failures), skips duplicate hashes (deleting the skipped file/cover through the storage helper), writes audit `Subida Material` per created material, returns counts.

**Success:** `201 { "message": "...", "created": 2, "skipped": 1, "materials": [ ... ] }`

**Errors:** `422` no items, >100, invalid metadata/type/link/cover; `429`.

**Note:** Because materials have no subjects, they appear in the global catalog but not on subject pages until a professor associates them.

**Atomicity caveat:** `uploadBatch` processes items sequentially without a transaction. If a later item fails, earlier materials may already be committed, while the controller's local-mode error cleanup deletes every uploaded file/cover path collected for the request, potentially leaving those earlier DB rows pointing to removed files.

---

### 41. `POST /api/materials/:id/approve`

**Access:** `Profesor`, `Superadmin`.

**Input:** `{ "subjectId": 5 }` (required; converted with `Number`).

**Action:** Loads the subject; requires Superadmin or `subject.hasProfessor(caller)`; sets the `material_subjects` row to `Aprobado`; sets material `Aprobado`; notifies subscribers; records `Aprobacion Material`.

**Success:** `200 { "message": "Material aprobado..." }`

**Errors:** `404` subject; `403` not the professor; invalid `subjectId` becomes `NaN` and typically yields `404`.

**Note:** The service does not verify that the association row exists before updating; the normal UI only calls it for a pending row. It also does not verify that the material exists: with a valid subject and nonexistent material id, the UPDATEs affect zero rows, notification persistence fails silently, and the route still returns `200` and writes an approval audit row.

---

### 42. `POST /api/materials/:id/reject`

**Access:** `Profesor`, `Superadmin`.

**Input:** `{ "subjectId": 5 }`.

**Action:** Requires subject ownership (or Superadmin); deletes the association; counts remaining associations; if zero **and** the material is `Pendiente`, marks it `Rechazado`, clears URL/cover/hash, and deletes stored files; records `Cancelacion Material`.

**Success:** `200 { "message": "Asociacion rechazada...", "rejected": true|false }`

**Errors:** `404` subject/material; `403` not the professor.

**Note:** Rejecting one subject does not remove the material from other subjects. `rejected=true` only when the whole pending material is rejected. If the last association is removed from an already-`Aprobado` material, the material stays `Aprobado` with no subjects, its files are kept, and `rejected=false`.

**Success:** `200 { "message": "Material asociado...", "subjectIds": [5, 6] }`

**Errors:** `404` material; `403` not a professor/not teaching a subject; `422` missing/invalid ids.

**Note:** This endpoint can associate a pending material without changing its global `estado`; such a material still needs approval to be visible on subject pages.

### 45. `PUT /api/materials/:id`

**Access:** `Profesor`, `Superadmin`.

**Fields:**

| `pages` | Optional; positive integer or empty to clear. |

**Notes:** Does not check that the user exists; returns an empty list for unknown ids. This endpoint includes the raw rows plus the derived `registroTipo`, but it does not join/enrich actor or target names.

## 4.8 Thematic Tags

### 60. `GET /api/thematic-tags`

**Access:** Public.

**Query:** accepted but currently ignored by the repository.

**Success:** `200 { "tags": [ { "id": 1, "nombre": "...", "categoria": "general", "creadoPor": null, "baneado": 0, "createdAt": null } ] }`

Ordering: category, then name.

**Mapping caveat:** `findAll`/`findById` pass raw snake_case rows into `ThematicTag`, which reads only `creadoPor` and `createdAt`. List, ban and delete responses therefore report `creadoPor: null` and `createdAt: null` even when the database has values. `POST` returns the newly saved in-memory tag, which has `creadoPor` set but no `createdAt` property.

---

### 61. `POST /api/thematic-tags`

**Access:** `Alumno`, `Profesor`, `Superadmin`.

**Input:**

| Field | Required | Default |
|---|---|---|
| `nombre` | yes | — |
| `categoria` | no | `general` |

**Action:** Trims values. If `(nombre, categoria)` exists and is not banned, returns the existing tag; if it is banned, returns `400`; otherwise inserts the tag.

**Success:** `201 { "tag": { ... } }` (also for an existing non-banned tag).

**Errors:** `400` missing name or banned existing tag. The service does not enforce the 100-character column limits, so overlong `nombre`/`categoria` values can surface as an untranslated DB `500`.

**Audit:** None currently, despite the service constructor receiving `AuditLogService`.

---

### 62. `PUT /api/thematic-tags/:id/ban`

**Access:** Superadmin.

**Action:** Sets `baneado = 1`; returns the updated tag object (`{ ...tag, baneado: 1 }`). A banned tag cannot be created again but remains listed.

**Success:** `200 { "tag": { ... } }`

**Errors:** `404`.

**Audit:** None currently.

---

### 63. `DELETE /api/thematic-tags/:id`

**Access:** Superadmin.

**Action:** Deletes the tag row. Material `categories` text is untouched.

**Success:** `200 { "message": "ok" }`

**Errors:** `404`.

**Audit:** None currently.

### 69. `PUT /api/profile`

**Access:** Any authenticated user.

**Input (all optional):**

| Field | Rules |
|---|---|
| `nombre`, `apellido` | 2–50 letters/spaces; required if present and non-empty. |
| `birthdate` | `YYYY-MM-DD`; past date with age 0–120; empty/`null` clears it. |
| `gender` | `Male`, `Female`, `Non-Binary`, `Other`; empty/`null`/`-` clears it. |
| `genderCustom` | Required for `Other`; 3–10 letters/spaces. |
| `city`, `country` | 2–50 letters/spaces. |
| `phone` | 7–20 characters from digits, `+`, `-`, spaces and parentheses. |
| `github`, `instagram`, `linkedin` | Full URL for the network or a handle of 3–100 characters. |
| `career`, `institute` | 2–80 characters. |
| `aboutMe` | Up to 300 characters. |
| `profilePicture` | Must be a default picture or a rank picture unlocked by the user's rank. |

**Action:** Validates and updates only the supplied fields. Empty text fields are stored as `'-'`; empty `gender` also clears `genderCustom`. A non-`Other` gender clears `genderCustom`.

**Success:** `200` with the same enriched payload as `GET /api/profile/:id` for the current user.

**Errors:** `404` user not found; `422` with keys such as `validation.required`, `validation.invalidData`, `validation.birthdate`, `validation.gender` or `validation.genderCustom`.

```json
  ]

```

### 71. `GET /api/reads`

**Access:** Any authenticated user.

**Success:** `200 { "materials": [ ... ] }` — current user's read materials, newest read first, with `isRead`/backlog flags attached.

**Notes:** Materials are loaded by read id and are not filtered by state.

---

### 72. `GET /api/reads/:materialId`

**Access:** Any authenticated user.

**Input:** path `materialId`.

**Success:** `200 { "read": true, "progress": { "materialId": 5, "currentPage": 25, "totalPages": 100, "status": "reading", "completed": false, "progress": 25, ... } }`

**Notes:** Returns `read: false` and `progress: null` when there is no read row or backlog row. This route does not verify that the material exists.

---

### 73. `POST /api/reads/:materialId/toggle`

**Access:** Any authenticated user.

**Input:** none.

**Action:** If a read row exists, deletes it (XP is not subtracted). Otherwise inserts the read, removes any backlog row, grants `+100 XP`, evaluates badges and notifies followers.

**Success:** `200 { "read": true|false, "xp": 350, "rankLevel": 2, "rankTitle": "..." }`

**Errors:** `404` unknown material.

**Notes:** The read insert uses `INSERT IGNORE`; notifications and badge evaluation run only on the first transition to read.

---

### 74. `PUT /api/reads/:materialId/progress`

**Access:** Any authenticated user.

**Input:**

| Field | Required | Rules |
|---|---|---|
| `currentPage` | yes in practice | Clamped to `0..totalPages`; `0` stores `pending`. |
| `totalPages` | no | Falls back to `materials.pages`; must resolve to a positive number. |

**Action:** Upserts the current page and total in `reading_backlog`. When `currentPage >= totalPages`, inserts a read row, removes the backlog row, grants `+100 XP` if it was not already read, evaluates badges and notifies followers.

**Success:** `200 { "read": { "materialId": 5, "currentPage": 100, "totalPages": 100, "status": "read", "completed": true, "progress": 100, "read": true, "inBacklog": false, ... } }`

**Errors:** `404` unknown material; `422 validation.materialPagesMissing` when neither `totalPages` nor `materials.pages` is positive.

**Notes:** The repository clamps `totalPages` up to at least `currentPage`. Repeating completion does not grant XP twice because the read row already exists.

---

### 75. `GET /api/backlog`

**Access:** Any authenticated user.

**Success:** `200 { "items": [ ... ] }` — current user's backlog, ordered by `updated_at` descending.

**Notes:** Same item shape and material filtering as `GET /api/users/:id/backlog`.

---

### 76. `POST /api/backlog/:materialId`

**Access:** Any authenticated user.

**Action:** Inserts a `pending` backlog row with `INSERT IGNORE`, so re-adding is idempotent.

**Success:** `201 { "added": true, "item": { "materialId": 5, "currentPage": 0, "totalPages": null, "status": "pending", "progress": 0, ... } }`

**Errors:** `404` unknown material.

---

### 77. `DELETE /api/backlog/:materialId`

**Access:** Any authenticated user.

**Success:** `200 { "removed": true|false }` — `false` when there was no row.

**Notes:** Does not verify that the material exists.

---

### 78. `POST /api/subscriptions/:userId`

**Access:** Any authenticated user.

**Action:** Follows another active user with `INSERT IGNORE` and evaluates follower/following badges for both users.

**Success:** `201 { "following": true, "followers": 3 }`

**Errors:** `404` unknown/inactive target; `422 validation.invalidData` when following yourself.

**Notes:** Repeating the follow is idempotent and returns the current follower count.

---

### 79. `DELETE /api/subscriptions/:userId`

**Access:** Any authenticated user.

**Success:** `200 { "following": false, "removed": true|false }`

**Notes:** Does not verify that the target user exists; `removed` is `false` when there was no follow row.

### 80. `GET /api/streaks`

**Access:** Any authenticated user.

**Success:** `200 { "streak": { "currentStreak": 2, "lastReadDate": "2026-10-29", "updatedAt": "..." } }`

**Notes:** A user with no streak row gets `{ "currentStreak": 0, "lastReadDate": null, "updatedAt": null }`. The streak is advanced only through heartbeat activity, not by opening the profile.

---

### 81. `POST /api/streaks/heartbeat`

**Access:** Any authenticated user.

**Input:**

| Field | Required | Rules |
|---|---|---|
| `materialId` | no | Must identify an existing material for time to accumulate. |
| `activeSeconds` | no | Accumulated active seconds for the session. |
| `deltaSeconds` | no | Increment since the last heartbeat; capped at 120. |

**Action:** Keeps an in-memory session keyed by `userId:materialId`; a session expires after 300 seconds without a heartbeat. At 300 active seconds, registers daily activity, updates the streak and sends streak notifications.

**Success:** `200 { "streak": { "currentStreak": 2, "lastReadDate": "...", "qualified": true, "activeSeconds": 300, "requiredSeconds": 300 } }`

**Notes:** Without a valid `materialId` the response has `qualified: false`, `activeSeconds: 0` and the current persisted streak. Sessions are process-local and are lost on restart.

---

### 82. `POST /api/streaks/reset`

**Access:** Any authenticated user.

**Input:** `{ "materialId": 5 }` (optional but required to remove a session).

**Success:** `200 { "reset": true|false }`

**Notes:** Deletes the in-memory session for the current user and material; it does not alter the persisted streak.

- Professor uploads are auto-approved.
- The professor must teach **every** selected subject.

## 7. Implementation Notes and Known Gaps

1. **JWT state staleness:** `verifyToken` trusts the token payload and does not re-query `estado`; account bans/deactivations take effect for new logins, not for already-issued tokens.
2. **Subject ownership:** `subject_professors` is authoritative; `subjects.profesor_id` is a cached primary professor.
3. **Global vs. subject catalogs:** `/api/materials/global` shows all approved materials, even unassigned ones. Subject pages require both material approval and an approved association.
4. **Duplicate professor upload:** associating an existing pending material as a professor does not change the material's global `estado`; only approval does.
5. **Approve safety:** `approveMaterial` updates association/material state without checking that the association or material exists. A valid subject with a nonexistent material id still returns `200` and writes an approval audit row. Normal UI flow uses valid pending rows.
6. **Observer privacy:** `GET /api/subscriptions/subject/:id/observers` does not check that the professor teaches the subject.
7. **No server pagination:** API list results are complete; the UI paginates.
8. **Audit coverage:** Tag operations are not audited. Unsubscribing is not audited. Login is not audited.
9. **Duplicate DB errors:** Some unique violations (career name, career-year name) are not translated and may return `500`.
10. **Empty updates:** `PUT /api/subjects/:id` accepts a no-op and still writes `Modificacion Materia`.
11. **Subject reject:** `reject-association` removes all professors but only changes `estado_asociacion` to `Pendiente` when it was already `Pendiente`.
12. **Material delete ambiguity:** The admin `DELETE /api/materials/:id` supports `?subjectId=` and then behaves like subject removal, not global deletion.
13. **Notification uniqueness:** `(usuario_id, subject_id, material_id)` is unique; re-publishing resets `read_at` and updates `created_at`.
14. **File cleanup:** Disk cleanup failures are logged; DB state may still change.
15. **Localized messages:** A service `message` key is translated by `ok()` only if it contains a dot. A literal message is returned as-is.
16. **Notifications can reference pending material:** professor association/duplicate paths notify subscribers without checking `materials.estado`.
17. **CORS and body parsing:** The server enables `cors()` with defaults and parses JSON/urlencoded bodies globally; multipart is handled per upload route.
18. **No refresh token:** Clients must log in again when the 2-hour JWT expires; `apiService` handles 401 by clearing the session.
19. **Default language:** `es`, unless `DEFAULT_LANGUAGE` is set.
20. **Test harness:** `NODE_ENV=testing` disables upload rate limiting and replaces page routes with the test harness at `/`.
21. **Role string exactness:** Authorization compares `Superadmin`, `Profesor`, `Alumno`; display translations do not change these values.
22. **Duplicate upload orphan:** a successful duplicate-hash upload leaves the newly stored file/cover in storage because cleanup runs only when the request fails in local mode.
23. **Public author email exposure:** `GET /api/materials/author/:id` returns name and email for any existing user id, without checking that the user authored materials or has a public role.
24. **No admin-account protection:** ban/unban/soft-delete accept any user id, including the caller or another Superadmin; there is no last-admin or self-protection rule.
25. **Batch partial failure:** `uploadBatch` is not transactional; a later item failure can leave earlier materials committed, while local-mode controller cleanup deletes every uploaded path collected for the request.
